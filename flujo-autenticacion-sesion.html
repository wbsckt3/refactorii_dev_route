1
Usuario hace clic en "Iniciar sesión con Google"
Google muestra el popup de autenticación
2
Google devuelve JWT con datos del usuario
El token contiene: email, nombre, foto, etc.
// auth.js - handleCredentialResponse() async function handleCredentialResponse(response) { // 1. Decodificar JWT de Google const responsePayload = decodeJwtResponse(response.credential); // responsePayload contiene: email, name, picture, etc. }
3
Guardar datos del usuario en localStorage
const formData = { Email: responsePayload.email, FullName: responsePayload.name, ImageURL: responsePayload.picture }; localStorage.setItem("formData", JSON.stringify(formData));
4
Llamar al backend para obtener/crear usuario
// Llamar al backend con el email const ok = await getUserByEmail(responsePayload.email); // Backend devuelve token JWT si el usuario existe if (data.tkn) { const token = data.tkn; const payload = JSON.parse(atob(token.split('.')[1])); const expiry = payload.exp * 1000; localStorage.setItem("refactorii_token", token); localStorage.setItem("token_expiry", expiry); localStorage.setItem("Email", payload.Email); }

2 Validación de Sesión en el Frontend

¿Cuándo se valida?

Al cargar cualquier página de la aplicación, se ejecuta la función validarToken() para verificar si el usuario está autenticado.

// dynamic-route-editor.html - validarToken() function validarToken() { const token = localStorage.getItem("refactorii_token"); const expiry = parseInt(localStorage.getItem("token_expiry") || "0", 10); // 1. ¿Hay token? if (!token || !expiry) { return false; // ❌ No autenticado } // 2. ¿Token expirado? if (Date.now() > expiry) { alert("Tu sesión ha expirado. Por favor vuelve a iniciar sesión."); localStorage.clear(); return false; // ❌ Sesión expirada } // 3. Token válido return true; // ✅ Autenticado }
✅ Control de Acceso

Si el token es válido, se muestra la aplicación. Si no, se muestra el overlay de login con el botón de Google Sign-In.

3 Validación en el Backend (Por Email)

⚠️ Importante: Validación por Email, NO por Token

El backend valida las peticiones usando el email enviado en las cabeceras, no el token. Esto se hace para evitar problemas de CORS.

// workflow.controller.js - verifyExercisesInTestAutomationPath() exports.verifyExercisesInTestAutomationPath = async (req, res) => { // 1. Obtener email de las cabeceras (NO del token) const userEmail = req.headers['x-user-email']?.toLowerCase().trim(); const pathId = req.headers['x-path-id']?.trim(); // 2. Validar que el usuario existe en la BD const user = await GoogleSigninUser.findOne({ Email: userEmail }).lean(); if (!user) { return res.status(404).json({ error: 'Usuario no encontrado' }); } // 3. Validar que el usuario tiene relación con una compañía const relations = await CompanyGoogleSigninUser.find({ googlesigninuserId: user._id.toString() }); if (relations.length === 0) { return res.status(403).json({ error: 'No autorizado' }); } // 4. Buscar y devolver la ruta const ruta = (user.testAutomationPlans || []).find( r => r.id === Number(pathId) ); return res.status(200).json({ success: true, ruta }); }

4 ¿Por qué se valida por Email y no por Token?

Aspecto Validación por Token Validación por Email (Actual)
Configuración CORS Compleja
Requiere permitir cabecera 'Authorization'		 Simple
Solo requiere 'x-user-email' y 'x-path-id'
Seguridad Alta
Token firmado y con expiración		 Media
Depende de validaciones en backend
Problemas CORS Sí
Navegador bloquea si no está configurado		 No
Funciona sin problemas de CORS
Validación Backend Verifica firma y expiración del token Verifica existencia de usuario y permisos
💡 Razones principales:
  • Problema CORS: Enviar Authorization: Bearer <token> requiere que el servidor permita esa cabecera en CORS, lo que complica la configuración.
  • El email es suficiente: El backend valida que el usuario existe, tiene relación con compañía y acceso a los datos solicitados.
  • El token se usa solo en frontend: Para control de sesión (mostrar/ocultar login) y validar que la sesión no ha expirado.

5 Flujo Completo del Sistema

🔑
1. Usuario hace Login con Google
Google autentica y devuelve JWT con datos del usuario
💾
2. Backend valida/crea usuario
Busca usuario por email, si no existe lo crea, devuelve token JWT
📦
3. Frontend guarda en localStorage
  • refactorii_token (JWT)
  • token_expiry (fecha expiración)
  • formData (datos del usuario: email, nombre, etc.)
✅
4. Al cargar página: Validación de token
  • Si válido → muestra aplicación
  • Si inválido → muestra login
🌐
5. Al hacer petición API
  • Frontend envía email en cabecera 'x-user-email'
  • NO envía token (por problemas CORS)
  • Backend valida usuario por email
  • Backend verifica permisos y devuelve datos

6 Aspectos de Seguridad

✓
Frontend: El token valida la sesión localmente. Si no hay token o está expirado, se muestra el login.
✓
Backend: Valida que el usuario existe, tiene relación con compañía y acceso a los datos solicitados.
⚠
Limitación actual: Si alguien conoce el email de otro usuario, podría hacer peticiones. Para mayor seguridad se puede:
  • Enviar el token como query param (menos seguro pero funciona con CORS)
  • Configurar CORS para permitir Authorization header
  • Usar un proxy en el mismo dominio

7 Resumen

📋 Puntos clave del sistema:
  • ✅ El token se guarda en localStorage después del login
  • ✅ El frontend valida el token para control de sesión
  • ✅ El backend valida por email (no por token) para evitar problemas CORS
  • ✅ El email se envía en la cabecera x-user-email
  • ✅ El token NO se envía en las peticiones API
